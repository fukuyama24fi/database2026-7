システム概要

作成日日： 2026年7月22日
題材： データベースを使った多部署AI設計シミュレーション

1. 作成するソフトウェアの概要

1.1 このソフトは何をするものか

このソフトは、データベース（PostgreSQL）とAIを使って、ソフトウェアの設計を進めるシミュレーションです。

普通の会社だと、CTO（技術責任者）が仕事を各部署に分け、社員が会議して設計書を作り、 部長がチェックして、最後に品質管理担当（CQO）が全体を見直します。 このソフトは、その流れをAIが代わりにやってくれます。

使い方は、run_project.py の中身を書き換えてから実行します。 main() 関数の先頭で project_id（プロジェクト名）と task_text（やってほしいこと）をセットします。 実行すると、AIが議論して設計書と「決まったことリスト（D-list）」を作ります。

1.2 処理の流れ

① CTOが「どの部署が何を担当するか」を決める ↓ ② 部長たちが配分内容にOKを出す（上流会議） ↓ ③ 各部署のAI社員が会議して設計書を作る ↓ ④ 部長が成果物をチェック（OK / やり直し） ↓ ⑤ CQOが部署間の矛盾がないか見る ↓ 矛盾があれば 部長会議 → 修正 → もう一度⑤へ ↓ 問題なければ ⑥ 最終成果物をフォルダに保存

1.3 使い方

順番コマンド何をするか
1python db/create_tables.pyDBにテーブルを作る（最初の1回だけ）
2python seed/run_seed.py社員・部長のデータをDBに入れる（最初の1回だけ）
3run_project.py を編集して python run_project.pyproject_id と task_text を書き換えてから実行
4フォルダを見るworkspaces/ 以下に結果が出る

1.4 特長

  • DBに記憶を保存する — 会話・要約・決まったことをDBに残す
  • いろいろな役割のAIが動く — CTO、部長、PM、社員、CQO など
  • 間違えたら直せる — 矛盾が見つかったら、やり直しや部分修正ができる
  • AIが使えなくても次を試す — Groq → Mistral → Gemini の順で切り替わる

2.2 フォルダの分け方

機能ごとにフォルダを分けました。1ファイルに全部書くとごちゃごちゃするので、 役割・会議・DB・記憶などに分けています。

datebase/ ├── run_project.py … ここから全部始まる ├── db/ … データベースの読み書き ├── meeting/ … 会議・議論 ├── roles/ … CTO, 部長, PM, CQO ├── memory/ … 決まったことの抽出・要約 ├── llm/ … AIを呼び出す ├── workspace/ … ファイルの読み書き ├── seed/ … 最初のデータ投入 └── workspaces/ … 実行結果がここに出る

2.3 データベースの考え方

AIの「覚えておく情報」を3段階に分けてDBに保存します。

種類DBのどこ何のため
短期recent_messages直近の会話（発言の続きを理解するため）
中期short_summary各ターンの要約をまとめた200字程度の文章。部長やCQOが「この部署は何を決めたか」を素早く把握するために使う
長期department_rooms_decisions議論で確定した決定事項（D-list）。何を決めたか・根拠・何ターン目かを保存し、やり直し時は status で取り消し管理する

2.4 AIの性格設計（anchor と persona）

各AIエージェントには、DBの agent_personas テーブルに2種類の情報を保存しています。

名前DB上の項目役割重要度
anchor
（専門ドメイン）		judgment_anchor「何を重視するか」「何を許さないか」など、判断の基準。部署ごとの専門領域（FEならUI実装、QAならテストなど）メイン
persona
（話し方）		style_personaトーンや言い回しなど、話し方の個性サブ

AIへの指示文（prompts/build_system_prompt.py）では、 まず anchor（判断軸）を「絶対に譲らない基準」として書き、 そのあとに persona（話し方）を添える形にしています。 部長の検収なども「自部署の anchor の範囲内だけで判断する」ルールになっています。

主なテーブル：

  • project_states — プロジェクトの状態
  • department_rooms — 部署ごとの「部屋」（議論の場）
  • department_rooms_decisions — 決まったこと（D-list）
  • department_members_master — 社員データ
  • agent_personas — AIの anchor（judgment_anchor）と persona（style_persona）

2.5 やり直しの仕組み

CQOが「部署Aと部署Bの内容が矛盾している」と見つけたとき、2通りの直し方があります。

  • 部分修正 — 問題のある決定だけ直す
  • Turn巻き戻し — あるターンから議論を最初からやり直す

どちらも、DB上で古い決定の status を cancelled（取り消し）に変えることで、 過去の記録を残しつつ「今有効な決定」だけ取り出せるようにしています。

3. プログラムの説明

3.1 メイン（run_project.py）

全部の流れをこの1ファイルから始めます。実行前に project_id と task_text を書き換えます。

def main():
    project_id = "proj_test_002"   # ← プロジェクトID（フォルダ名などに使われる）
    task_text = "Webアプリ版ポモドーロタイマーのログイン機能を設計してください"  # ← やってほしいこと

    create_project(project_id)                 # ① DBにプロジェクト登録
    assignments = cto_assign_tasks(task_text)    # ② CTOが部署配分
    assignments = run_top_meeting(...)           # ③ 部長がOKか確認

    for assignment in assignments:
        result = run_department_room(...)      # ④ 各部署で議論

    while cqo_round < 3:                       # ⑤ CQO監査（最大3回）
        if 問題なし: break
        部長会議 → 修正 → 再議論

    collect_final_outputs(...)                 # ⑥ 成果物をまとめる

3.2 テーブル作成（db/create_tables.py）

PostgreSQLに接続して、必要なテーブルを作ります。 D-list用テーブルには「取り消しフラグ（status）」と「何ターン目で決まったか（origin_turn）」を入れて、 やり直しに対応できるようにしました。

3.3 部署ルーム（meeting/run_one_department.py）

1つの部署で行う処理です。

  1. DBにルームを登録
  2. スキルに合う社員をDBから選ぶ
  3. PMが役割を割り当て
  4. 社員全員が数ターン議論する
  5. 決まったことをD-listとしてDBに保存
  6. 部長がチェック（OKなら終了、NGならやり直し）

部長のやり直しは最大2回。3回目は強制でOKにします。

3.4 AIへの指示文（prompts/build_system_prompt.py）

DBから読んだ anchor と persona を使って、AIへの指示文を組み立てます。

anchor = persona["judgment_anchor"]   # メイン：判断軸（専門ドメイン）
style = persona["style_persona"]    # サブ：話し方

# 指示文では anchor を先に、「絶対に譲らない基準」として書く
# そのあと persona で話し方を指定する

3.5 社員の1発言（meeting/member_turn.py）

社員1人が発言するときの処理です。

  1. DBから anchor・persona と直近の会話を読む
  2. AIに設計案を考えさせる
  3. 結果をDBと design.txt に保存する

3.6 AI呼び出し（llm/ask_llm.py）

Groq、Mistral、Gemini の3つを用意しています。 1つがエラー（使いすぎで止められた等）になったら、次のAIに自動で切り替わります。

5. 考察

5.1 DBを使って「覚えさせる」ことについて

このソフトで一番こだわったのは、AIの情報をDBに保存することです。 AIは1回の会話しか覚えられないので、 「直近の会話」「短い要約」「決まったこと」をDBに分けて保存しています。

特にD-listの status が便利でした。 矛盾が見つかって直すとき、古いデータを消さずに cancelled にするだけで、 「今有効な決定」だけ取り出せます。

5.2 軽量LLMでも動かすこと（サブ実験）

今回は、高価な大きなAIモデルではなく、 軽量LLM（llama-3.1-8b-instant など）でも動くようにすることも目的の1つでした。 これはサブ実験です。

最初はAIの返答がバラバラで、JSON形式で返してくれないこともありました。 でも、プロンプトの書き方を直したり、JSON解析のエラー処理を入れたり、 AIが使えなくなったら別のAIに切り替える機能を入れたりするうちに、 少しずつ回答が安定してきました。

実際に動かしたときも、Groqが「使いすぎです（429エラー）」となって Mistralに切り替わり、そこから処理が続いていました（図1参照）。 軽量モデル単体では不安定でも、切り替えやエラー処理を組み合わせれば 実用的に動かせるとわかりました。

5.3 やり直し機能について

CQOが部署間の矛盾を見つけたとき、 「部分修正（問題の部分だけ直す）」と 「Turn巻き戻し（議論ごとやり直す）」の2パターンを作りました。 軽い矛盾なら部分修正の方が早く終わります。

5.4 作れなかったこと（今後追加したい機能）

① CEOとユーザーの対話機能

もともとは、CEOがユーザーと何度か会話して、要望をはっきりさせてからCTOに渡す予定でした。

イメージ：

ユーザー「ログイン機能を作って」 ↓ CEO「SNSログインも必要ですか？」 ↓ ユーザー「はい、Googleログインがいい」 ↓ CEO「わかりました。CTO、Googleログイン付きのログイン機能をお願いします」 ↓ CTOが部署配分を開始

でも今は、run_project.py の中に要件テキストを直接書いているだけなので、 CEOの部分は未実装です。ユーザーがチャットで要件を伝えられるようにしたいです。

② Pythonコード（.py）の自動生成

今のソフトは「設計書（design.txt）」と「決まったこと（d_list.txt）」を出力しますが、 実際に動く .py ファイルは作れません。

例えばフロントエンド部署ならHTML/CSSのコード、 バックエンド部署ならFlaskのAPIコードを自動で書いて workspaces/ に保存できるようにしたいです。

今は member_turn.py が design.txt だけ更新していますが、 ここに「.pyファイルも書く」処理を追加すれば実現できそうです。

③ その他、やりたいこと

  • 依存関係のない部署を同時に動かす（今は1つずつ順番）
  • 議論の様子が見えるWeb画面を作る（今は黒い画面だけ）
  • DB部分の自動テストを書く（AI部分は結果が毎回違うのでテストが難しい）

5.5 まとめ

今回作ったのは、DBをAIの「記憶」として使い、 複数のAIが協力してソフトウェア設計を進めるシミュレーションです。

CEOとの対話や.pyファイル生成など、まだ入れられなかった機能はありますが、 基本の流れ（配分→議論→チェック→監査→修正）は動くところまで作れました。
